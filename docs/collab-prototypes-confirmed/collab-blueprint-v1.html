身份架构

三层切分：不是 A 或 B，是按信任边界各归各位

两位评审独立得出同一结论——Q1"登录二选一"是个假命题。正确切法：

accounts收缩为纯内部员工登录。已 bcrypt，不是安全负债；问题是内外混装，把 ~15 条外部行迁走后冻结边界。
portal_users复用为外部长期身份锚（客户/工厂/货代/报关行）。公司级账号+角色+scope 全现成，重新定位为"magic-link 优先、口令可选"——身份是锚，认证方式可插拔。
magic_links访问票，不是身份。它是 3–4 天短效邀请票（193 条 supplier 链接 177 条已过期），撑不住长期访问——token 只认证一次引导动作，身份和会话另立。

客户旅程：免登录看追踪 → magic_link 一次性引导 → 绑定/创建 portal_user 并签发 session → 之后凭 session 反复访问 → 过期用邮件 magic-link step-up 续期 → 后期小程序 = 同一身份上的一个渠道。

统一提交层

一张收件箱吃掉所有外部写入

  • collab_submissions（staging 收件箱）+ collab_submission_events（append-only 留痕）两张新表，纯 additive 上线，不动任何现有表。
  • 覆盖四类协同：工厂确认价格、客户补料、货代填舱单、报价接受——靠 intent 区分，payload 用 jsonb（顺带规避 SQL_ASCII 汉字字节截断）。
  • 三张 0 行确认表（factory_confirmations / invoice_collab_confirm_overrides / customs confirmed_*）零数据迁移：前两张改代码指向后废弃，confirmed_* 列保留作 apply 落地目的地。
  • apply 护栏（写进代码规范）：dry-run 出 diff → 人点确认 → SELECT 验命中 → UPDATE 带业务键 WHERE → 写 applied_to + event → psql 回读验真。主表只 additive 到独立列，永不覆盖报关原始真值。
  • 对外读投影默认拒绝、显式白名单——成本/买价物理不出 API，不再靠"记得别 SELECT 那列"。

CREATE TABLE collab_submissions (
  id             bigserial PRIMARY KEY,
  submission_uid uuid NOT NULL DEFAULT gen_random_uuid(), -- 对外只用它
  magic_link_id  integer REFERENCES magic_links(id),      -- 哪张票授权
  portal_user_id uuid REFERENCES portal_users(id),        -- 有身份则挂靠
  submitter_role text NOT NULL,                           -- factory_booking/customer/...
  submitter_ident text,                                   -- email/公司码快照
  intent         text NOT NULL,  -- factory_price_confirm|customer_backfill
                                 -- |fwd_manifest|quote_accept
  sheet_type     text,           -- → collab_sheet_templates.sheet_type
  target_kind    text NOT NULL,  -- order|customs_item|quote|booking
  target_ref     text NOT NULL,  -- 业务键: order_no/decl_key/...（无硬FK）
  payload        jsonb NOT NULL, -- 外部提交原文
  field_diffs    jsonb,          -- 审核时算出 [{field,old,new}]
  attachments    jsonb,          -- [{name,url,sha256}]
  status         text NOT NULL DEFAULT 'submitted',
                 -- submitted|under_review|applied|rejected|superseded
  applied_to     jsonb,          -- 实际写了哪 [{table,pk,cols}]
  reviewed_by    text, reviewed_at timestamptz,
  applied_at     timestamptz, reject_reason text,
  content_hash   text,           -- 幂等去重（Codex）
  supersedes_id  bigint REFERENCES collab_submissions(id),
  source_ip      text,
  created_at     timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ux_cs_uid    ON collab_submissions(submission_uid);
CREATE INDEX ix_cs_queue  ON collab_submissions(status)
       WHERE status IN ('submitted','under_review');
CREATE INDEX ix_cs_target ON collab_submissions(target_kind, target_ref);
CREATE UNIQUE INDEX ux_cs_dedupe ON collab_submissions(content_hash)
       WHERE status <> 'rejected';

CREATE TABLE collab_submission_events (
  id bigserial PRIMARY KEY,
  submission_id bigint NOT NULL REFERENCES collab_submissions(id),
  actor  text NOT NULL,   -- external:factory:CP-xx | internal:damon | system
  action text NOT NULL,   -- submitted|reviewed|applied|rejected|reverted
  detail jsonb,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ix_cse_sub ON collab_submission_events(submission_id);

风险

最可能死在哪三件事上

  1. 蓝图过载、半途而废——库里 6 套半成品就是前科。保命：禁 big-bang，P1 先上拿正反馈；不收敛就停在当前阶段也不塌。
  2. 成本价泄漏给客户——一个角色判断 bug 的距离。保命：身份物理分层 + 读投影默认拒绝白名单 + 面向客户的 payload 永不含成本列 + 沿用成本词硬拦。
  3. apply 误写主表真源——"漏 WHERE 全表置 done"的前科要在这里防住。保命：五步护栏（diff→人确认→SELECT 验命中→业务键 WHERE→回读验真），主表只 additive。

附加（Codex）：警惕配置引擎长成 JSONB 怪物——collab_sheet_templates 只管表单与展示；权限归身份层、提交归 staging、审计归 events，各归各表。
